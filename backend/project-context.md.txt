1. PRODUCT OVERVIEW

FinVigil AI is an India-only portfolio intelligence SaaS. It consolidates holdings across multiple brokers, tracks cost basis via FIFO, computes capital-gains tax (STCG/LTCG), and helps users prepare for ITR filing. It is read-only — it never executes trades.

The 5 Core Features (product promise)


🏦 Multi-Broker Dashboard — consolidate Zerodha, Groww, Upstox, WazirX, CoinDCX into one wealth view (one total value, one P&L, one tax picture).
🌾 Tax-Loss Harvesting — identify losing positions to sell before year-end to offset gains and reduce tax.
🎬 Portfolio Replay — rewind the portfolio to any past date and watch it evolve trade by trade.
🎲 Monte Carlo Simulation — run thousands of future scenarios for a probability range of portfolio value.
🎙️ Voice Journal — record voice notes per trade, timestamped, linked to trades, searchable.


Supporting capabilities (infrastructure that powers the 5 features)

Broker OAuth sync, CSV import, FIFO cost basis, STCG/LTCG tax engine, CA-readable export, corporate action adjustments, F&O trade storage.

Scope boundary (from BRD)

"Not a tax preparer/filer — exports + User/CA input fields only." FinVigil produces capital-gains figures and CA-assistance exports; the CA completes the actual ITR. Default Assessment Year: AY 2026-27 / FY 2025-26.

4. ARCHITECTURE RULES (STRICT — never violate)


Layering: Model (schema only) → Repository (DB access only) → Service (business logic only) → API (request/response only). Never mix layers.
One model per file. UUID primary keys via UUIDMixin. Timestamps via TimestampMixin.
Money math: always Decimal(str(value)), never float. Compare with Decimal("0"), not integer 0.
Transaction atomicity: commit happens ONCE in get_db(). All repository writes use self.db.flush() — NEVER self.db.commit().
Dependency injection: each API file has a get_*_service() function that builds repos → services.
Idempotency: all trade-insertion paths use the single shared generate_trade_idempotency_hash() from app/core/idempotency.py.

Phase 5.3 — F&O P&L Engine


New table fno_pnl_entries (migration db/migrations/002_fno_pnl_entries.sql): one row per FIFO-matched buy↔sell leg. Columns: user_id, instrument_id, buy_trade_id (nullable), sell_trade_id, symbol, quantity, buy_price, sell_price, buy_time (nullable), sell_time, profit_loss, is_intraday, assessment_year, timestamps. 3 indexes + tenant-isolation RLS policy (consistent with 001_initial_hardening.sql).
6 new files + 1 modified: models/fno_pnl_entry.py, repositories/fno_pnl_repository.py, schemas/fno_pnl.py, services/fno_pnl_service.py, api/v1/fno_pnl.py (all NEW) + main.py (added fno_pnl router — now 13 routers).
FIFO matching: per instrument, buys and sells each sorted by execution_time ascending; a buy queue is consumed FIFO by sells. Each match writes one entry with profit_loss = (sell_price - buy_price) × matched_qty. All money math is Decimal(str()).
Intraday vs positional split: is_intraday = (buy_time.date() == sell_time.date()). Intraday F&O = speculative business income; positional = non-speculative. Stored per entry and summed in the summary endpoint. Verified: intraday -₹669.50 + positional -₹3887.00 = total -₹4556.50.
SELL > BUY edge case (Option A): when a sell has no matching buy left (expired/shorted contract), the entry gets buy_trade_id=NULL, buy_time=NULL, buy_price=0, profit_loss = sell_price × quantity. Verified on NIFTY2661623000PE (130 sells, 0 buys) → profit_loss 416.00 = 3.20 × 130.
Assessment year mapping: reuses the month≥4 rule (get_assessment_year duplicated locally — tech-debt item 6). Test trades are June 2026 (FY 2026-27) → AY 2027-28. DB verified: GROUP BY assessment_year → 2027-28, 33 entries, total -4556.50, intraday -669.50, positional -3887.00.
Open positions (unmatched buys) are NOT stored — derived on demand by _compute_open_positions() (consumes total sold qty against buys FIFO, returns net open qty + weighted-avg buy price per instrument). open_positions_count is consistent across POST /fno/calculate, GET /fno/pnl, and GET /fno/positions (all report 3, counted per instrument).
Reconstruction engine: calculate_all_fno_pnl() is delete-and-rebuild — it wipes the user's fno_pnl_entries and recomputes from trades every call. Fully idempotent and deterministic. This is the first reconstruction engine in the project and directly addresses the KNOWN PRODUCTION RISK (Section 5) for the F&O side: F&O P&L is now always rebuildable from source-of-truth trades.
Endpoints: POST /fno/calculate, GET /fno/pnl/, GET /fno/pnl/{assessment_year} (literal before parameterized), GET /fno/positions. Summary response includes a business-income disclaimer (PGBP, ITR-3, rate/turnover/audit determined by CA).
Isolation boundary held: equity FIFO, realized_gains, holding_lots, tax_engine_service, and trade_service were NOT touched by the F&O engine. F&O P&L writes only to fno_pnl_entries, never to realized_gains (equity capital gains only).


Phase 5.3 (part 2) — Equity Reconstruction Engine


Purpose: rebuild holding_lots and realized_gains from source-of-truth trades + corporate_action_adjustments. Closes the Section 5 KNOWN PRODUCTION RISK for equity. No DB migration (uses existing tables).
Files: services/reconstruction_service.py, api/v1/reconstruction.py, schemas/reconstruction.py (all NEW) + repositories/holding_lot_repository.py and repositories/realized_gain_repository.py (added delete_by_user()) + main.py (added reconstruction router — now 14 routers).
Reuses HoldingLotService.create_holding_lot + consume_lots_fifo so the replay is byte-identical to the live buy/sell pipeline in trade_service. No FIFO logic is re-implemented.
Delete order matters: realized_gains deleted FIRST (its holding_lot_id FK is ON DELETE RESTRICT), then holding_lots. Both repository deletes use flush(), never commit().
Replay order (deliberate): (1) replay ALL equity trades in execution_time order — buys create lots, sells consume FIFO → realized_gains; (2) THEN reapply corporate actions as a post-pass in applied_at order, adjusting open/partial lots bought strictly before applied_at (qty × ratio, price ÷ ratio). Corporate actions applied AFTER trades — NOT chronologically interleaved — because that reproduces existing behavior exactly (a split only touches lots still open when applied) and matches the "reapply after rebuilding" contract. corporate_action_adjustments rows are source of truth and are NOT recreated (no duplicate-guard collision).
Only equity trades processed (instrument_type == "equity"); F&O trades ignored (they have their own engine).
Idempotent: delete-and-rebuild every call → identical result. Safe to run repeatedly.
Endpoint: POST /reconstruction/equity?user_id=... Returns counts: realized_gains_deleted, holding_lots_deleted, holding_lots_created, realized_gains_created, corporate_actions_reapplied, lots_adjusted_by_corporate_actions.
VERIFIED on RELIANCE test data (5 trades, 1 stock_split 2:1): snapshot before → rebuild → snapshot after produced IDENTICAL financial content (3 lots: 10@2800 closed, 40@1375 open ×2; 2 realized_gains: 5@STCG pl 500, 5@LTCG pl 2000; total P&L ₹2,500). Ran twice → byte-identical (idempotency proven). Corporate action correctly skipped the closed Lot1 (stayed 2800) and split the two open lots (2750→1375).

Endpoints: POST /crypto/ingest (buy/sell), GET /crypto/tax/{assessment_year}. Crypto tax computed on demand (no summary table). Response carries a 115BBH/194S disclaimer.
VERIFIED (AY 2026-27, 3 coins): BTC gain ₹5L, ETH loss ₹5L, DOGE gain ₹1k → total_vda_gains ₹501,000, total_vda_losses -₹500,000, taxable ₹501,000 (loss NOT set off), vda_tax ₹150,300 (flat 30%), total_tds ₹40,000 (BTC 25k + ETH 15k; DOGE ₹6k sell below threshold → no TDS), net_tax_payable ₹110,300. 8. F&O HANDLING (Option C — full isolation)

Decision: F&O trades are stored as source-of-truth but completely isolated from the equity FIFO engine until Phase 5.3 builds a dedicated F&O engine.


trade_service.py has process_fno_buy_trade() and process_fno_sell_trade() — both store the trade only, no holding lots, no realized_gains.
Routing (in both CSV import and Zerodha sync): fno + buy → process_fno_buy_trade; fno + sell → process_fno_sell_trade; everything else → process_trade.
Why: equity FIFO assumes 365-day STCG/LTCG, indefinite holding, capital-gains treatment. F&O expires worthless, is taxed as business income, has lot-size sizing, and same-strike-different-expiry issues. Running F&O through equity FIFO would corrupt realized_gains and create phantom holdings.
Verified: 60 F&O trades stored, fno_holding_lots = 0 (isolation proven).
Phase 5.3 will: build F&O P&L engine + reconstruct F&O positions from stored trades.

11. BUG FIXES APPLIED (verified)

Transaction Atomicity (Tier 1) — FIXED ✅


Root cause: base.py create()/delete() committed per-call, breaking atomicity across multi-write operations (a sell = trade + lot update + realized_gain). Failed sells left orphan trades + locked idempotency_hash + silent tax understatement.
Fix (4 files together): session.py get_db() now yield → commit(), except: rollback(); raise, finally: close(). base.py, dashboard_repository.py, tax_summary_repository.py all use flush() only.
Proven by: oversell test (sell 9999 of 40 held) → 400 error AND zero orphan rows (rollback works).


Tax Set-Off (Tier 2 Item 1) — FIXED ✅


tax_engine_service.py Step 5: a net STCG loss now offsets LTCG gain (and vice versa) before the LTCG exemption. Hand-verified 4 cases; regression-tested existing data unchanged.


Honest Labeling (Tier 2 Item 3) — FIXED ✅ (Option C)


Added a disclaimer field (default text) to TaxSummaryResponse — no cess math, no schema migration. States it's a capital-gains estimate only, excludes cess/surcharge/other income.


datetime.utcnow() deprecation — PARTIALLY FIXED

17. PHASE 11.2 — REAL AUTHENTICATION (ES256 / Supabase JWKS)

Approach: Option B (ECC P-256), matching this Supabase project's actual JWT signing key type (confirmed live: GET {SUPABASE_URL}/auth/v1/.well-known/jwks.json returns alg=ES256, kty=EC, crv=P-256 — the legacy HS256 shared-secret approach would NOT have worked on this project).

New files


app/core/auth.py — get_current_user_id(authorization: str = Header(...)) -> UUID FastAPI dependency. Verifies the JWT signature using the ES256 public key fetched from Supabase's JWKS endpoint, checks audience="authenticated", extracts and returns the 'sub' claim as a UUID. Every failure mode (missing header, malformed token, unknown kid, bad signature, expired, wrong audience, non-UUID sub) returns 401 — never 500.
JWKS handling: module-level in-memory cache of {kid: PyJWK}, same pattern as price_service.py's cache. Refetches Supabase's JWKS when a token's kid is unseen (first call) OR when jwt.InvalidSignatureError is raised against the cached key (the specific failure mode key rotation causes) — retried exactly once, not on every failure type, so an expired/malformed token fails fast without wasting an HTTP round-trip.
Dependency: PyJWT==2.13.0 added (cryptography was already installed, required for ES256/EC support). requirements.txt regenerated via pip freeze (was UTF-16 encoded from a prior Windows pip freeze; kept that convention, now written UTF-8 — functionally the same file, more portable encoding).
app/core/config.py — added SUPABASE_URL (default "https://ozbzbesayaxmptsyaznb.supabase.co", overridable via env var).

Router rollout — all api/v1/*.py files


Every user_id: UUID query param became user_id: UUID = Depends(get_current_user_id) across broker.py, holding.py, portfolio.py, tax.py, tax_export.py, corporate_action.py, csv_import.py, dashboard.py, fno_pnl.py, reconstruction.py, crypto.py, trade.py, realized_gain.py, and zerodha.py (login + sync only — see exception below). 14 files touched, ~25 endpoints protected.
