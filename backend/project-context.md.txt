1. PRODUCT OVERVIEW

FinVigil AI is an India-only portfolio intelligence SaaS. It consolidates holdings across multiple brokers, tracks cost basis via FIFO, computes capital-gains tax (STCG/LTCG), and helps users prepare for ITR filing. It is read-only — it never executes trades.

The 5 Core Features (product promise)


🏦 Multi-Broker Dashboard — consolidate Zerodha, Groww, Upstox, WazirX, CoinDCX into one wealth view (one total value, one P&L, one tax picture).
🌾 Tax-Loss Harvesting — identify losing positions to sell before year-end to offset gains and reduce tax.
🎬 Portfolio Replay — rewind the portfolio to any past date and watch it evolve trade by trade.
🎲 Monte Carlo Simulation — run thousands of future scenarios for a probability range of portfolio value.
🎙️ Voice Journal — record voice notes per trade, timestamped, linked to trades, searchable.


Supporting capabilities (infrastructure that powers the 5 features)

Broker OAuth sync, CSV import, FIFO cost basis, STCG/LTCG tax engine, CA-readable export, corporate action adjustments, F&O trade storage.

Scope boundary (from BRD)

"Not a tax preparer/filer — exports + User/CA input fields only." FinVigil produces capital-gains figures and CA-assistance exports; the CA completes the actual ITR. Default Assessment Year: AY 2026-27 / FY 2025-26.

4. ARCHITECTURE RULES (STRICT — never violate)


Layering: Model (schema only) → Repository (DB access only) → Service (business logic only) → API (request/response only). Never mix layers.
One model per file. UUID primary keys via UUIDMixin. Timestamps via TimestampMixin.
Money math: always Decimal(str(value)), never float. Compare with Decimal("0"), not integer 0.
Transaction atomicity: commit happens ONCE in get_db(). All repository writes use self.db.flush() — NEVER self.db.commit().
Dependency injection: each API file has a get_*_service() function that builds repos → services.
Idempotency: all trade-insertion paths use the single shared generate_trade_idempotency_hash() from app/core/idempotency.py.

Phase 5.3 — F&O P&L Engine


New table fno_pnl_entries (migration db/migrations/002_fno_pnl_entries.sql): one row per FIFO-matched buy↔sell leg. Columns: user_id, instrument_id, buy_trade_id (nullable), sell_trade_id, symbol, quantity, buy_price, sell_price, buy_time (nullable), sell_time, profit_loss, is_intraday, assessment_year, timestamps. 3 indexes + tenant-isolation RLS policy (consistent with 001_initial_hardening.sql).
6 new files + 1 modified: models/fno_pnl_entry.py, repositories/fno_pnl_repository.py, schemas/fno_pnl.py, services/fno_pnl_service.py, api/v1/fno_pnl.py (all NEW) + main.py (added fno_pnl router — now 13 routers).
FIFO matching: per instrument, buys and sells each sorted by execution_time ascending; a buy queue is consumed FIFO by sells. Each match writes one entry with profit_loss = (sell_price - buy_price) × matched_qty. All money math is Decimal(str()).
Intraday vs positional split: is_intraday = (buy_time.date() == sell_time.date()). Intraday F&O = speculative business income; positional = non-speculative. Stored per entry and summed in the summary endpoint. Verified: intraday -₹669.50 + positional -₹3887.00 = total -₹4556.50.
SELL > BUY edge case (Option A): when a sell has no matching buy left (expired/shorted contract), the entry gets buy_trade_id=NULL, buy_time=NULL, buy_price=0, profit_loss = sell_price × quantity. Verified on NIFTY2661623000PE (130 sells, 0 buys) → profit_loss 416.00 = 3.20 × 130.
Assessment year mapping: reuses the month≥4 rule (get_assessment_year duplicated locally — tech-debt item 6). Test trades are June 2026 (FY 2026-27) → AY 2027-28. DB verified: GROUP BY assessment_year → 2027-28, 33 entries, total -4556.50, intraday -669.50, positional -3887.00.
Open positions (unmatched buys) are NOT stored — derived on demand by _compute_open_positions() (consumes total sold qty against buys FIFO, returns net open qty + weighted-avg buy price per instrument). open_positions_count is consistent across POST /fno/calculate, GET /fno/pnl, and GET /fno/positions (all report 3, counted per instrument).
Reconstruction engine: calculate_all_fno_pnl() is delete-and-rebuild — it wipes the user's fno_pnl_entries and recomputes from trades every call. Fully idempotent and deterministic. This is the first reconstruction engine in the project and directly addresses the KNOWN PRODUCTION RISK (Section 5) for the F&O side: F&O P&L is now always rebuildable from source-of-truth trades.
Endpoints: POST /fno/calculate, GET /fno/pnl/, GET /fno/pnl/{assessment_year} (literal before parameterized), GET /fno/positions. Summary response includes a business-income disclaimer (PGBP, ITR-3, rate/turnover/audit determined by CA).
Isolation boundary held: equity FIFO, realized_gains, holding_lots, tax_engine_service, and trade_service were NOT touched by the F&O engine. F&O P&L writes only to fno_pnl_entries, never to realized_gains (equity capital gains only).


Phase 5.3 (part 2) — Equity Reconstruction Engine


Purpose: rebuild holding_lots and realized_gains from source-of-truth trades + corporate_action_adjustments. Closes the Section 5 KNOWN PRODUCTION RISK for equity. No DB migration (uses existing tables).
Files: services/reconstruction_service.py, api/v1/reconstruction.py, schemas/reconstruction.py (all NEW) + repositories/holding_lot_repository.py and repositories/realized_gain_repository.py (added delete_by_user()) + main.py (added reconstruction router — now 14 routers).
Reuses HoldingLotService.create_holding_lot + consume_lots_fifo so the replay is byte-identical to the live buy/sell pipeline in trade_service. No FIFO logic is re-implemented.
Delete order matters: realized_gains deleted FIRST (its holding_lot_id FK is ON DELETE RESTRICT), then holding_lots. Both repository deletes use flush(), never commit().
Replay order (deliberate): (1) replay ALL equity trades in execution_time order — buys create lots, sells consume FIFO → realized_gains; (2) THEN reapply corporate actions as a post-pass in applied_at order, adjusting open/partial lots bought strictly before applied_at (qty × ratio, price ÷ ratio). Corporate actions applied AFTER trades — NOT chronologically interleaved — because that reproduces existing behavior exactly (a split only touches lots still open when applied) and matches the "reapply after rebuilding" contract. corporate_action_adjustments rows are source of truth and are NOT recreated (no duplicate-guard collision).
Only equity trades processed (instrument_type == "equity"); F&O trades ignored (they have their own engine).
Idempotent: delete-and-rebuild every call → identical result. Safe to run repeatedly.
Endpoint: POST /reconstruction/equity?user_id=... Returns counts: realized_gains_deleted, holding_lots_deleted, holding_lots_created, realized_gains_created, corporate_actions_reapplied, lots_adjusted_by_corporate_actions.
VERIFIED on RELIANCE test data (5 trades, 1 stock_split 2:1): snapshot before → rebuild → snapshot after produced IDENTICAL financial content (3 lots: 10@2800 closed, 40@1375 open ×2; 2 realized_gains: 5@STCG pl 500, 5@LTCG pl 2000; total P&L ₹2,500). Ran twice → byte-identical (idempotency proven). Corporate action correctly skipped the closed Lot1 (stayed 2800) and split the two open lots (2750→1375).

8. F&O HANDLING (Option C — full isolation)

Decision: F&O trades are stored as source-of-truth but completely isolated from the equity FIFO engine until Phase 5.3 builds a dedicated F&O engine.


trade_service.py has process_fno_buy_trade() and process_fno_sell_trade() — both store the trade only, no holding lots, no realized_gains.
Routing (in both CSV import and Zerodha sync): fno + buy → process_fno_buy_trade; fno + sell → process_fno_sell_trade; everything else → process_trade.
Why: equity FIFO assumes 365-day STCG/LTCG, indefinite holding, capital-gains treatment. F&O expires worthless, is taxed as business income, has lot-size sizing, and same-strike-different-expiry issues. Running F&O through equity FIFO would corrupt realized_gains and create phantom holdings.
Verified: 60 F&O trades stored, fno_holding_lots = 0 (isolation proven).
Phase 5.3 will: build F&O P&L engine + reconstruct F&O positions from stored trades.



9. CURRENT DATABASE SCHEMA (key tables)

instruments

id, isin (varchar, nullable, unique), symbol (varchar, not null), type (enum: equity/fno/mf/crypto), name (varchar nullable in DB; ORM treats not-null, uses symbol as fallback), timestamps.


ORM note: Python attribute is instrument_type, mapped to DB column type via mapped_column("type", ...).


broker_connections

id, user_id (FK auth.users CASCADE), broker_name (enum: zerodha/groww/upstox/wazirx/coindcx/csv), status (enum: active/disconnected/syncing/error — NO pending), credentials_kms_id (varchar nullable — holds Vault secret UUID), timestamps. Unique on (user_id, broker_name).

trades

Source of truth. idempotency_hash UNIQUE constraint = sha256(broker_connection_id:broker_trade_id). Has instrument_id, broker_trade_id, trade_type, quantity, price, execution_time.

holding_lots

quantity_bought, quantity_remaining, buy_price, buy_date, status (open/partial/closed), source_trade_id, instrument_id.

realized_gains

sell_trade_id, holding_lot_id, quantity_sold, buy_price, sell_price, buy_date, sell_date, holding_days, gain_type (STCG/LTCG — NULLABLE; NULL for crypto), income_type (equity_capital_gains/fno_business_income/crypto_vda, default equity_capital_gains), profit_loss. Shared table for equity capital gains + crypto VDA, distinguished by income_type.

tds_credit_ledger

id, user_id, source_trade_id (FK trades, nullable), amount, timestamp, timestamps. Holds 1% VDA TDS records (Phase 5.4).

tax_summaries

16 columns: totals, taxable amounts, rates, exemption, taxes, total_tax_liability, calculated_at. (Response schema adds a disclaimer field.)

Approach: Option B (ECC P-256), matching this Supabase project's actual JWT signing key type (confirmed live: GET {SUPABASE_URL}/auth/v1/.well-known/jwks.json returns alg=ES256, kty=EC, crv=P-256 — the legacy HS256 shared-secret approach would NOT have worked on this project).

New files


app/core/auth.py — get_current_user_id(authorization: str = Header(...)) -> UUID FastAPI dependency. Verifies the JWT signature using the ES256 public key fetched from Supabase's JWKS endpoint, checks audience="authenticated", extracts and returns the 'sub' claim as a UUID. Every failure mode (missing header, malformed token, unknown kid, bad signature, expired, wrong audience, non-UUID sub) returns 401 — never 500.
JWKS handling: module-level in-memory cache of {kid: PyJWK}, same pattern as price_service.py's cache. Refetches Supabase's JWKS when a token's kid is unseen (first call) OR when jwt.InvalidSignatureError is raised against the cached key (the specific failure mode key rotation causes) — retried exactly once, not on every failure type, so an expired/malformed token fails fast without wasting an HTTP round-trip.

25. POST-STAGE-2D BACKEND ROOT-CAUSE FIXES — REAL 500 + SLOW AY SWITCHING

Triggered by two live symptoms after Stage 2D shipped: a genuine "500 Internal Server Error" console message on the /tax page, and continued slow page loads / AY switching. Investigated deeply per explicit instruction (real EXPLAIN ANALYZE, real query counts, real concurrency tests) before changing anything.

25.1 Problem 2 (slowness) — root cause found and measured

This project's Supabase Postgres runs on the Session Pooler in ap-south-1 (Mumbai). Measured directly: even on an already-open, warm connection, every single SQL round trip costs ~90-450ms (confirmed via repeated SELECT 1 on the same connection — pure network latency, not query cost: EXPLAIN ANALYZE showed the actual trades query executes server-side in 0.07ms). This means query COUNT, not query complexity, dominates latency here.

Confirmed N+1: TradeRepository.get_by_user() had no eager-load on Trade.instrument (SQLAlchemy default relationship loading is lazy). FnoPnlService._group_fno_trades() (called by get_pnl_summary AND get_open_positions, i.e. hit on every single F&O-touching request and every AY switch) touches trade.instrument for every trade in a loop to check its type — one lazy-load SQL round trip per DISTINCT instrument. Measured against the real test user (133 trades, 21 distinct instruments) with real query-level instrumentation:
  GET /fno/pnl/{ay}: 23 SQL statements (21 were the N+1 lazy-loads), 16,492ms total wall time — the N+1 queries alone cost 8,991ms.
  GET /crypto/tax/{ay}: 2 SQL statements (no N+1 there), 913ms — still ~450ms/query from pure RTT even with zero N+1, confirming the network-latency baseline.
The equity reconstruction engine (reconstruction_service.py) had the exact same anti-pattern (t.instrument.instrument_type filtered in Python after fetching all trades) — not yet on the user-facing slow path, but fixed for the same reason.

Also found, lower severity but real "at scale" debt: crypto_tax_service.calculate_crypto_tax and tax_engine_service.calculate_tax_summary fetched a user's ENTIRE gain/TDS history (every AY, all-time) and filtered to one AY in Python, instead of filtering by date range in SQL. Doesn't cost extra ROUND TRIPS today (small test data), but fetches strictly more rows every year as real trading history accumulates.

Fixes:
  trade_repository.py — get_by_user() now uses joinedload(Trade.instrument) (one JOIN, zero extra round trips). Added get_by_user_and_instrument_type() — filters by instrument type at the SQL level via a JOIN to instruments, instead of fetching every trade type and filtering in Python.
  fno_pnl_service.py — _group_fno_trades() now calls the new SQL-scoped method instead of get_by_user() + Python filtering.
  reconstruction_service.py — same fix applied to the equity replay's trade fetch.
  tax_utils.py — added get_ay_date_range(assessment_year), the exact inverse of get_assessment_year() (AY string -> [FY-start, FY-end) UTC datetime range). Correctness-proven BEFORE use in any query that touches real tax numbers: a standalone script checked get_assessment_year(day) -> get_ay_date_range(that_ay) contains day for every one of 4,018 consecutive days (2020-01-01 through 2030-12-31), including every March 31 / April 1 boundary explicitly — 0 failures.
  realized_gain_repository.py / tds_ledger_repository.py — added get_by_user_income_type_and_date_range() / get_by_user_and_date_range(), SQL-level AY-range filtering.
  crypto_tax_service.py / tax_engine_service.py — now call the SQL-scoped methods instead of fetch-all-then-filter-in-Python.

Real before/after (same test user, same script, direct service-layer calls against the live DB):
  GET /fno/pnl/{ay}: 23 SQL statements -> 2. 16,492ms -> 2,819ms (~5.9x).
  GET /crypto/tax/{ay}: 912ms -> 307ms (~3x — no N+1 removed here, gain is from SQL-level date scoping + warm-connection reuse).
Correctness re-verified after the rewrite against already-known-good figures (not just "doesn't crash" — actual Decimal-equal values): crypto AY 2026-27 (gains 501000, losses -500000, vda_tax 150300.00, TDS 40000, net 110300.00), F&O AY 2027-28 (total -4556.50, intraday -669.50, positional -3887.00, 33 entries), F&O AY 2026-27 correctly empty, equity STCG AY 2025-26 (500.00) — 12/12 PASS.

25.2 Problem 1 (the real 500) — root cause found live, not just inferred

Could not reproduce the exact original 500 via direct service-layer calls (all 9 real endpoint x AY combinations succeeded cleanly against the live DB and real user), and the then-running backend's complete log had zero tracebacks. But while writing a correctness-verification script, a REAL, LIVE failure was caught directly — both in an isolated script AND, moments later, on an actual HTTP request against the running uvicorn server (GET /api/v1/fno/pnl/2026-27):

  psycopg2.OperationalError: ... FATAL: (EMAXCONNSESSION) max clients reached in session mode - max clients are limited to pool_size: 15

Root cause: Supabase's Session Pooler enforces a HARD SERVER-SIDE cap of 15 concurrent connections for this project, regardless of what the app requests. db/session.py was configured for pool_size=20 + max_overflow=20 = 40 — more than double what Supabase actually allows. Any burst past 15 concurrent connections (the dashboard alone fires 9 parallel Promise.all calls; a second tab or a couple of prefetched AY-tab requests trivially exceeds 15, and the F&O N+1 bug above held each request's connection open far longer than necessary, widening the collision window) threw this OperationalError from inside get_db()'s connection checkout. With no exception handler anywhere in the app (confirmed via code review — main.py had none), this fell straight through to Starlette's bare, unlogged default 500 — exactly matching what the frontend's console showed, and exactly why it couldn't be found in the server log: nothing was ever writing it there. In one observed instance during this investigation, the same error was severe enough to crash the entire uvicorn worker process.

Fixes:
  main.py — added a global @app.exception_handler(Exception) that logs a full traceback server-side and returns a clean, consistent {"detail": "Internal server error..."} 500 instead of a silent, untraceable one. Verified this does NOT intercept normal HTTPException flows — a real 401 was re-tested post-fix and still returns cleanly.
  db/session.py — pool_size/max_overflow lowered to respect Supabase's real ceiling. NOT a single confident number on the first attempt: pool_size=10+max_overflow=2 (12) still failed under a direct 20-concurrent-connection stress test (7/20 failed) because Supabase's 15-limit is PROJECT-WIDE, not per-process — the already-running backend was concurrently holding part of the budget while the stress-test script's own pool tried to claim up to 12 more. Lowering further to pool_size=6+overflow=2 (8) still produced 2/20 failures under the same test (likely transient — Supabase's pooler doesn't instantly reclaim a just-closed client's slot). Final, verified-clean config: pool_size=5 + max_overflow=1 (6 total) — re-ran the identical 20-concurrent-connection stress test after allowing connection state to settle: 20/20 succeeded, 0 failures. This leaves real headroom under the 15 ceiling for anything else that might be drawing from the same shared budget (a second local process, a psql session, a future Celery worker). If real traffic ever needs more concurrent DB work than 6, the correct fix is Supabase's Transaction Pooler (much higher effective limit) or a paid tier's higher cap — NOT raising this past what Session Pooler actually allows.

26. OWNERSHIP-CHECK GAP CLOSED (the last disclosed pre-production security gap from Phase 11.2)

The gap: 3 endpoints required a valid Supabase token (Phase 11.2) but fetched the requested resource by ID ONLY — no filter on the authenticated user_id. A logged-in user could fetch another user's holding lot, trade, or realized gain by guessing/enumerating a UUID. Confirmed by reading the code before changing anything: GET /holdings/{lot_id} → HoldingLotService.get_lot_by_id() → BaseRepository.get_by_id() → `WHERE id = :id`, no user_id. Fix — same repository/service pattern used everywhere else in this codebase (a dedicated, explicitly-named scoped method, not a generic unscoped one):

27. PHASE 7 — TAX-LOSS HARVESTING ENGINE

BRD alignment: FR-HAR-01/02 (FIFO-based loss identification, equity STCG/LTCG + exemption; VDA excluded — crypto has no set-off under 115BBH, so it is never a harvest candidate by design, not an oversight) and FR-HAR-04's spirit (surface a sell list + estimated saving). FR-HAR-03 (scheduled 06:00 IST Celery job + 60s polling) and FR-HAR-04's literal "Simulate in Replay" deep link are NOT built — both depend on infrastructure this project doesn't have yet (Celery/Redis is Phase 12; Replay is Phase 8, not yet built). Computed on demand instead, same pattern as the crypto tax engine (no summary table — always reflects current holding_lots + live prices).

27.1 Backend

New files: app/schemas/harvesting.py, app/services/harvesting_service.py, app/api/v1/harvesting.py. main.py — added the harvesting router (now 16 routers, 38 routes).

HarvestingService(holding_repository, realized_gain_repository, price_service) — get_harvest_candidates(user_id, ay) walks every OPEN/PARTIAL holding_lot (via the already-existing get_active_lots_by_user(), same joinedload-eager-loaded method dashboard_service.py uses — no new N+1 risk introduced), batches a live price lookup via the existing PriceService.get_prices() (same silent-fallback, 5-min-cache, single-batched-kite.quote() mechanism dashboard already uses — no new pricing code written), and for each lot: unrealized_loss = (current_price_or_cost_basis − buy_price) × qty, included only if negative. gain_type uses the exact same >365-day threshold as holding_service.consume_lots_fifo (LTCG_HOLDING_DAYS_THRESHOLD = 365, named to match). Sorted biggest-tax-saving-first before returning (the frontend's requested order — computed once server-side, not re-sorted client-side).

Honest price fallback (not a bug): if no live Zerodha token is active, current_price falls back to cost basis (current_price = buy_price), which makes unrealized_loss exactly 0 for that lot — it can never register as a candidate. This is deliberate: the engine does not fabricate a loss it cannot observe. Verified directly against the real test user's data: no active Zerodha token right now → 0 candidates across all AYs, which is the honestly correct result, not a bug (see 27.3).

LTCG "exemption check" (estimated_tax_saving) — the one genuinely non-trivial piece of business logic in this phase, so it got a from-scratch design decision, not just wiring: the ₹1,25,000 LTCG exemption applies to a whole year's NET LTCG position, not per-transaction, so a new LTCG loss only creates a REAL tax saving if the user already has taxable LTCG gains this AY for it to offset. HarvestingService._existing_ltcg_gains(user_id, ay) queries the user's ALREADY-REALIZED LTCG gains for the AY via the existing SQL-scoped realized_gain_repository.get_by_user_income_type_and_date_range() (built in Section 25 — reused here, not reinvented), summed once per get_harvest_candidates() call (not per-candidate — doing it per-candidate would be the exact N+1 shape found and fixed in Section 25, since this value doesn't depend on which lot is being evaluated). If existing gains > ₹1,25,000: full 12.5% applies to each LTCG candidate's loss. If existing gains are at/below the exemption: estimated_tax_saving = ₹0 for LTCG candidates — honestly reflecting that there is no current-year taxable LTCG for the loss to offset, not a naive blind 12.5% on every LTCG loss regardless of context. STCG has no exemption in Indian tax law (confirmed no complication needed): estimated_tax_saving = loss × 20% always. Documented simplification (same spirit as the crypto TDS per-transaction-threshold simplification elsewhere in this project): checks the CURRENT realized position only, not cumulative across the candidate list being evaluated in the same call.

get_harvest_summary(user_id, ay) — total_harvestable_loss (signed negative, sum of candidates' unrealized_loss — matches the signed convention every other P&L figure in this app already uses, e.g. F&O total_pnl, so the same Money tone="auto" signed frontend treatment applies unmodified), total_estimated_tax_saving, candidate_count, days_until_march_31 (derived from the existing get_ay_date_range()'s end boundary minus one day — reuses Section 25's AY-range helper rather than re-deriving FY-end logic a third time in this codebase; clamped to max(0, ...) so an already-closed AY never shows a negative countdown).

27.4 DASHBOARD OVERFLOW FIX — Total Portfolio Value card (user-reported, real bug)

Symptom: adding the Tax Health Score widget (27.2.1) made the hero metric row lg:grid-cols-5 — 5 equal columns, including Total Portfolio Value's Money size="xl" (36px statement numerals). "₹1,10,000" overflowed its card boundary at desktop width.

Root cause, quantified before fixing (not just eyeballed): at a 1280px viewport, the dashboard's actual available content width is 992px (1280 − 240px sidebar − 48px main padding, still under the max-w-5xl 1024px cap). 5 columns across 992px with 4× 16px gaps left each card only ~186px outer / ~146px inner width after p-5 padding. "₹1,10,000" at size="xl" needs ≈223px (IBM Plex Mono tabular digits, ~21.6px/char × 8 digits/commas, plus the ₹ symbol and .00 fraction) — 77px wider than the space available. Every other card on that row (Day P&L, Unrealized P&L, Tax Liability, Tax Health Score) uses the smaller size="lg" (24px) and was NOT overflowing — this was specifically a hero-number-in-too-narrow-a-column problem, not a general grid problem.

Fix — two independent grids, not one crowded row (dashboard-client.tsx):
  Row 1 (grid-cols-1 sm:grid-cols-2 lg:grid-cols-4): Total Portfolio Value, Day P&L, Unrealized P&L. Total Portfolio Value gets lg:col-span-2 — this is still the SAME 4-column grid the dashboard had before Tax Health Score existed, so Day P&L and Unrealized P&L keep their original, already-proven-working column width (~236px unit at 1280px) — nothing else got narrower to make room for the fix. Total Portfolio Value's card grows to ~488px outer / ~448px inner, ~2x the space its 223px-wide number needs.
  Row 2 (grid-cols-1 sm:grid-cols-2): Tax Liability (TaxMeterCard) + Tax Health Score, each now a genuine half-width card (~488px outer at 1280px) instead of a cramped 1/5 slot — more room than either card has ever had, not just enough to clear the overflow.
  lg:col-span-2 only takes effect at the lg breakpoint (≥1024px) — Tailwind's responsive utilities are min-width-based and don't retroactively affect the sm 2-column state, so at tablet width Total Portfolio Value sits as a normal 1-span card alongside one sibling, not forced to double width prematurely.

Verified — pixel math worked through for both required widths before considering this done, not just tested at one size:
  Desktop 1280px (992px effective content width): Total Portfolio Value's 448px inner width vs its 223px-wide number = ~2x headroom.
