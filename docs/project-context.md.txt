1. PRODUCT OVERVIEW

FinVigil AI is an India-only portfolio intelligence SaaS. It consolidates holdings across multiple brokers, tracks cost basis via FIFO, computes capital-gains tax (STCG/LTCG), and helps users prepare for ITR filing. It is read-only — it never executes trades.

The 5 Core Features (product promise)


🏦 Multi-Broker Dashboard — consolidate Zerodha, Groww, Upstox, WazirX, CoinDCX into one wealth view (one total value, one P&L, one tax picture).
🌾 Tax-Loss Harvesting — identify losing positions to sell before year-end to offset gains and reduce tax.
🎬 Portfolio Replay — rewind the portfolio to any past date and watch it evolve trade by trade.
🎲 Monte Carlo Simulation — run thousands of future scenarios for a probability range of portfolio value.
🎙️ Voice Journal — record voice notes per trade, timestamped, linked to trades, searchable.


Supporting capabilities (infrastructure that powers the 5 features)

Broker OAuth sync, CSV import, FIFO cost basis, STCG/LTCG tax engine, CA-readable export, corporate action adjustments, F&O trade storage.

Scope boundary (from BRD)

"Not a tax preparer/filer — exports + User/CA input fields only." FinVigil produces capital-gains figures and CA-assistance exports; the CA completes the actual ITR. Default Assessment Year: AY 2026-27 / FY 2025-26.

4. ARCHITECTURE RULES (STRICT — never violate)


Layering: Model (schema only) → Repository (DB access only) → Service (business logic only) → API (request/response only). Never mix layers.
One model per file. UUID primary keys via UUIDMixin. Timestamps via TimestampMixin.
Money math: always Decimal(str(value)), never float. Compare with Decimal("0"), not integer 0.
Transaction atomicity: commit happens ONCE in get_db(). All repository writes use self.db.flush() — NEVER self.db.commit().
Dependency injection: each API file has a get_*_service() function that builds repos → services.
Idempotency: all trade-insertion paths use the single shared generate_trade_idempotency_hash() from app/core/idempotency.py.



5. SOURCE OF TRUTH vs DERIVED DATA

Source of truth (irreplaceable):


trades — the raw record of what happened. The foundation everything derives from.
broker_connections, instruments, corporate_action_adjustments — external facts.


Derived (rebuildable from trades + corporate actions):


holding_lots ← built from buys, consumed by sells (FIFO)
realized_gains ← built from sells via FIFO
tax_summaries ← computed from realized_gains (fully rebuildable; recomputed every call)
dashboard_projections ← from holdings + live prices


⚠️ KNOWN PRODUCTION RISK: There is currently NO "rebuild from trades" function. holding_lots and realized_gains are built incrementally and CANNOT be reconstructed if corrupted. A reconstruction engine should be built (planned as part of Phase 5.3, which has to replay trades anyway).

7. PHASE DETAILS & KEY DECISIONS

Phase 6.1 — Tax Engine Core


tax_summaries table (16 cols + disclaimer field on response).
get_assessment_year(sell_date): month ≥ 4 → FY starts that year; AY = FY+1. Verified: 2025-06-15 → AY 2026-27.
Rates: STCG 20% (0.20), LTCG 12.5% (0.125), LTCG exemption ₹1,25,000.
Endpoints: POST /tax/calculate, GET /tax/summary/, GET /tax/summary/{assessment_year} (route order matters — literal before parameterized).


Phase 6.2 — CA-Readable Tax Export


Extended ca_export_jobs with assessment_year VARCHAR(9) + export_type VARCHAR(50) (both nullable).
POST /tax/export returns CapitalGainsExportResponse (summary + per-transaction detail + disclaimer).
Computed on-demand (not stored); creates audit row with status='completed' (synchronous, no Celery).
Export field names deliberately renamed for honesty: total_tax_liability → total_tax_estimate, etc.
Design decision: extend existing ca_export_jobs (BRD alignment) rather than create a new table; Phase 11.1 will add s3_url/bundle fields to the same table.


Phase 6.3 — Corporate Action Adjustments


corporate_action_adjustments table (id, user_id, instrument_id, action_type, ratio, applied_at, timestamps).
Handles stock_split and bonus_issue: open/partial lots bought before action date get quantity × ratio, buy_price ÷ ratio; investment preserved.
Duplicate guard via get_duplicate(). POST /corporate-actions/apply, GET /corporate-actions/.
Verified: 2:1 split on RELIANCE → 2 lots adjusted, 20→40 qty, 2750→1375 price.


Phase 4.6 — CSV Import (Zerodha Tradebook)


Two-layer design: csv_parser_service.py (pure file parsing, zero DB) + csv_import_service.py (orchestration).
Zerodha tradebook format: header at row 14 (0-indexed), unnamed first/last columns dropped, ISIN nullable (null for F&O), supports .xlsx and .csv.
Columns used: Trade ID→broker_trade_id, Symbol, ISIN, Trade Date, Segment (EQ/FO), Trade Type, Quantity, Price, Order Execution Time.
POST /csv-import/tradebook (multipart upload). Returns CsvImportResponse (total_rows, imported, skipped, errors).
Verified: 60 F&O trades imported, 0 skipped, 0 errors.


Phase 4.5 — Zerodha OAuth Connection


Credentials split: ZERODHA_API_KEY + ZERODHA_API_SECRET in .env (app-level); per-user access_token in Supabase Vault; Vault secret UUID in broker_connections.credentials_kms_id.
Flow: GET /brokers/zerodha/login (creates connection + returns Kite login URL) → user logs in → Zerodha redirects with request_token → GET /brokers/zerodha/callback (exchanges via HMAC-SHA256 → access_token → Vault → marks active).
vault_repository.py is the only file using raw SQL (Vault functions are Postgres functions, not ORM tables); all values parameterized.
Vault API: vault.create_secret(secret, name, desc) → UUID; vault.update_secret(id, ...); read via SELECT decrypted_secret FROM vault.decrypted_secrets WHERE id = :id.
Daily token expiry handled by manual re-login (no Celery yet); update_secret() refreshes the same Vault entry in place.
Verified: OAuth callback → connected: true, status: active; Vault round-trip (store→retrieve→decrypt) confirmed.


Phase 4.7 — Zerodha Data Sync


Option A chosen: trades only (not holdings). Keeps trades as single source of truth; holdings stay derived via FIFO.
Added to zerodha_service.py: _get_kite_client() (builds authenticated KiteConnect from Vault token) + sync_today_trades() (fetches kite.trades(), routes through the existing trade pipeline).
kite.trades() fields: trade_id, tradingsymbol, transaction_type (BUY/SELL), quantity, average_price, fill_timestamp, exchange.
Exchange → instrument_type mapping: NFO/BFO → fno, everything else → equity.
Reuses the same generate_trade_idempotency_hash() → OAuth-synced and CSV-imported trades auto-deduplicate against each other.
POST /brokers/zerodha/sync returns CsvImportResponse (reused).

8. F&O HANDLING (Option C — full isolation)

Decision: F&O trades are stored as source-of-truth but completely isolated from the equity FIFO engine until Phase 5.3 builds a dedicated F&O engine.


trade_service.py has process_fno_buy_trade() and process_fno_sell_trade() — both store the trade only, no holding lots, no realized_gains.
Routing (in both CSV import and Zerodha sync): fno + buy → process_fno_buy_trade; fno + sell → process_fno_sell_trade; everything else → process_trade.
Why: equity FIFO assumes 365-day STCG/LTCG, indefinite holding, capital-gains treatment. F&O expires worthless, is taxed as business income, has lot-size sizing, and same-strike-different-expiry issues. Running F&O through equity FIFO would corrupt realized_gains and create phantom holdings.
Verified: 60 F&O trades stored, fno_holding_lots = 0 (isolation proven).
Phase 5.3 will: build F&O P&L engine + reconstruct F&O positions from stored trades.



9. CURRENT DATABASE SCHEMA (key tables)

instruments

id, isin (varchar, nullable, unique), symbol (varchar, not null), type (enum: equity/fno/mf/crypto), name (varchar nullable in DB; ORM treats not-null, uses symbol as fallback), timestamps.


ORM note: Python attribute is instrument_type, mapped to DB column type via mapped_column("type", ...).


broker_connections

id, user_id (FK auth.users CASCADE), broker_name (enum: zerodha/groww/upstox/wazirx/coindcx/csv), status (enum: active/disconnected/syncing/error — NO pending), credentials_kms_id (varchar nullable — holds Vault secret UUID), timestamps. Unique on (user_id, broker_name).

trades

Source of truth. idempotency_hash UNIQUE constraint = sha256(broker_connection_id:broker_trade_id). Has instrument_id, broker_trade_id, trade_type, quantity, price, execution_time.

holding_lots

quantity_bought, quantity_remaining, buy_price, buy_date, status (open/partial/closed), source_trade_id, instrument_id.

realized_gains

sell_trade_id, holding_lot_id, quantity_sold, buy_price, sell_price, buy_date, sell_date, holding_days, gain_type (STCG/LTCG), profit_loss.

tax_summaries

16 columns: totals, taxable amounts, rates, exemption, taxes, total_tax_liability, calculated_at. (Response schema adds a disclaimer field.)

corporate_action_adjustments

user_id, instrument_id, action_type, ratio (numeric 18,8), applied_at, timestamps.

ca_export_jobs

id, user_id, status (enum, default pending), s3_url (nullable), assessment_year (varchar9 nullable), export_type (varchar50 nullable), timestamps.

vault.secrets (Supabase Vault)

Managed by Vault. Read decrypted via vault.decrypted_secrets view.

11. BUG FIXES APPLIED (verified)

Transaction Atomicity (Tier 1) — FIXED ✅


Root cause: base.py create()/delete() committed per-call, breaking atomicity across multi-write operations (a sell = trade + lot update + realized_gain). Failed sells left orphan trades + locked idempotency_hash + silent tax understatement.
Fix (4 files together): session.py get_db() now yield → commit(), except: rollback(); raise, finally: close(). base.py, dashboard_repository.py, tax_summary_repository.py all use flush() only.
Proven by: oversell test (sell 9999 of 40 held) → 400 error AND zero orphan rows (rollback works).


Tax Set-Off (Tier 2 Item 1) — FIXED ✅


tax_engine_service.py Step 5: a net STCG loss now offsets LTCG gain (and vice versa) before the LTCG exemption. Hand-verified 4 cases; regression-tested existing data unchanged.


Honest Labeling (Tier 2 Item 3) — FIXED ✅ (Option C)


Added a disclaimer field (default text) to TaxSummaryResponse — no cess math, no schema migration. States it's a capital-gains estimate only, excludes cess/surcharge/other income.


datetime.utcnow() deprecation — PARTIALLY FIXED


Fixed in tax_summary_repository.py (→ datetime.now(timezone.utc)). Still present in tax_summary.py model default — flagged for cleanup.

Kite API constraints (important)
